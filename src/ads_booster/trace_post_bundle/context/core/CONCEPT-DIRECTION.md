# 컨셉 해석과 상황별 촬영 설계

상태: 2026-09-14 귀여움 촬영 방향 사용자 승인 반영 · 스킬 실행 규칙 연결.
적용 범위: 모든 컨셉의 촬영 설계. 새로운 템플릿·국가별 문구·배경 생성 기능의 지원 선언이 아니다.

제품 실행은 IMAGE-RULES와 RUN-POLICY의 계약을 사용하며 이 문서를 촬영 설계 기준으로 함께 읽는다. 프롬프트 C·검수·이력 비교·문서 스냅샷 경로가 연결된 배포 버전에서만 자동 실행에 적용된 것으로 판단한다.

## 1. 질문 없이 시작하고 해석의 출처를 구분한다

사용자가 컨셉을 지정하면 카드의 합의된 취향과 승인 레퍼런스를 우선 읽는다. 새 컨셉은 이름/짧은 설명만으로도 임시 방향을 세운다. 부족한 세부 취향을 모두 사용자에게 질문하지 않는다. 서로 충돌하는 필수 요구처럼 진행을 막는 모호함만 질문한다.

각 해석에는 `사용자 합의 / 레퍼런스 관찰 / 에이전트 가설` 중 출처를 기록한다. 자동 생성의 성공이나 무응답을 선호 승인으로 취급하지 않는다. 결과가 어긋나면 해석 문제와 이미지 구현 실패를 먼저 구분한다. 구현 실패 때문에 사용자 설명을 더 요구하지 않는다.

## 2. 유지 범위를 네 가지로 나눈다

| 범위 | 내용 | 저장 위치 |
|---|---|---|
| 컨셉 공통 | 이어갈 취향·정서, 피할 상충된 인상 | concepts 카드 본문 |
| 상황 필수 | 활동에 필요한 자세·물체 지지·날씨 적합성·촬영 가능한 손 배치 | 해당 게시물 설계 |
| 게시물별 표현 | 의상·소품·색·소재·빛·폰 위치·구도 | 해당 게시물 설계와 실제 관찰 |
| 같은 게시물의 국가별 공통 | 선택한 배경 디자인과 촬영 연출/프롬프트 | 해당 런의 공통 기록 |

구체적인 옷이나 색을 처음 골랐다고 컨셉의 영구 필수 조건으로 올리지 않는다. 사용자가 명시적으로 정한 고정 특징은 존중한다. 예시는 닫힌 선택 목록도, 매번 전부 넣어야 하는 체크리스트도 아니다.

필수 조건을 적을 때는 ‘이 표현을 바꿔도 같은 활동이 가능한가?’를 확인한다. 가능하면 이번 연출 선택이다. 아침 확인에 폰을 평평하게 놓는 것은 필수가 아니며, 폰이 선택한 지지면에서 안정적으로 놓이는 것은 물리적 조건이다. 선택한 연출 안의 조건을 다른 게시물에도 강제하지 않는다.

## 3. 상황을 정한 다음 표현을 고른다

1. 이번 컨셉이 전달할 인상을 짧게 정리한다. 인구통계만으로 취향을 대체하지 않는다.
2. 그 취향이 자연스럽게 드러날 생활 순간을 선택한다. 장소 이름뿐 아니라 무엇을 하다가 어떤 순간에 폰을 찍는지 적는다.
3. 상황에 맞는 의상·소품·소재·빛을 고르고 각각의 역할을 설명한다. 모든 물건에 컨셉 장식을 추가하지 않지만, 일괄적인 ‘소품을 적게’ 규칙으로 컨셉의 취향을 지우지도 않는다. 화면을 가린 상태에서도 주변의 조합이 의도한 취향과 어울리는지는 보조 기준이다.
4. 본인이 직접 찍을 수 있는 시점을 설계한다. 촬영용 기기를 든 손 하나는 화면 밖에 있다고 가정한다. 남은 손으로 화면용 폰을 들거나 폰을 안정된 곳에 놓을 수 있다. 양손이 다른 일에 쓰이는데 자기 시점으로 촬영하는 모순을 피한다. 무릎 위 폰은 본인이 내려다보는 관점이다. 얼굴은 노출하지 않는다.
5. 화면이 주인공이라는 목적과 가독성을 유지한다. 점유율·각도 하나를 모든 상황에 고정하지 않는다. 작은 글자가 읽히지 않으면 미확인으로 기록한다. 손톱의 특정 색이나 길이는 사용자가 요구하지 않는 한 스타일 합격 조건이 아니다.

생성 모델이 프롬프트에 없는 생활 소품을 추가할 수 있다. 추가됐다는 사실과 품질 판단을 분리한다. 상황과 컨셉을 자연스럽게 설명하고 화면을 방해하지 않는 추가는 허용할 수 있다. 임의 문구·로고, 컨셉보다 강한 시선 경쟁, 물리적 모순, 최근 장면마다 반복되는 같은 추가 조합은 결함 또는 관찰 대상으로 기록한다. 모든 소품을 사전에 열거해 창의성을 막지 않는다.

## 4. 취향의 일관성과 복제 같은 반복을 구분한다

최근 확인된 게시물의 상황·폰 배치·구도·의상/소재·주변 요소 조합을 비교한다. 일부 요소가 같다는 이유로 반려하지 않는다. 여러 요소가 함께 반복되어 화면만 교체한 사진처럼 보일 때, 컨셉 유지에 필요하지 않은 표현을 조정한다. 모든 요소를 강제로 바꾸거나 특정 의상을 금지하지 않는다.

완료 이력과 실험 결과는 구분한다. 실험은 명시적으로 전달한 비교 자료일 때만 참고하고 승인된 완료 런으로 등록하지 않는다. 이력이 없으면 없다고 기록하고, 여러 후보를 만드는 경우 후보끼리 비교한다. 생성 전 의도와 실제 생성된 반복은 별도로 기록한다.

후보마다 ‘겹치는 조합 / 바꿀 표현 / 유지해도 되는 표현 / 이유’를 기록한다. 같은 금지 문장을 모든 후보에 복사하지 않는다. 컵 하나를 빼도 지지면·폰 배치·구도 조합이 그대로면 충분한 변화라고 단정하지 않는다. 수정 전후를 비교했다고 보고하려면 최초 설계/프롬프트와 수정본을 별도 보존한다. 최초 기록이 없으면 사후 설명으로 표시한다.

## 5. 생성 전 기록과 생성 후 검수

게시물 설계 기록에는 다음을 남긴다.

- 컨셉 인상과 출처, 상황/활동
- 컨셉 때문에 유지할 것 / 상황 때문에 필요한 것 / 이번만의 표현
- 촬영하는 손·보이는 손·폰 지지·시점
- 최근 비교 대상과 반복시킨 요소/바꾼 조합 및 이유
- 컨셉 내 국가별 고정 연출, 생성에 실제 전달할 프롬프트

검수는 `해석이 적절한가 / 실제로 구현됐는가`를 분리한다. 취향의 연결, 상황 차이, 조합 반복, 셀프 촬영 가능성, 화면 보존/가독성을 각각 관찰한다. 해석이 좋다는 이유로 생성물을 통과시키지 않는다. 사용자 취향 일치와 모델의 성공률은 소수 결과로 확정하지 않는다.

### 이미지 호출 직전: 최종 프롬프트 자체를 대조한다

설계 요약이 아니라 실제 전달할 최종 문장을 읽고 아래 항목의 근거 문장과 판정을 남긴다. 모순은 사용자에게 떠넘기지 않고 호출 전에 수정한다. 수정본을 다시 검사하고, 해결하지 못한 필수 모순이 있으면 이미지를 호출하지 않고 원인을 기록한다. ‘자체 검수 완료’ 한 줄로 대신하지 않는다.

1. **손 역할:** 촬영 손 1개 + 화면에 보일 수 있는 다른 손 최대 1개로 각 동작을 배정한다. ‘한 손은 물병, 다른 손은 폰, 촬영 손은 화면 밖’은 세 손 요구다. 폰을 안정된 곳에 놓거나 소품을 내려놓아 해결한다. 보이는 손이 없어도 된다.
2. **지지와 시점:** 폰이 놓이는 면과 기울기가 물리적으로 가능한지, 촬영자의 위치에서 해당 화면/신체가 보이는지 확인한다. 화면을 보여주려고 설명 없는 전용 받침을 추가하거나 자기 시점과 몸통 정면을 동시에 요구하지 않는다.
3. **필수와 선택:** §2의 질문으로 재분류하고, 여러 후보의 구체적 표현을 공통 의무/금지로 바꾸지 않았는지 확인한다.
4. **설계와 문안 일치:** 손·소품·상황·시점·장식 개수에 대한 설명을 최종 문장과 대조한다. ‘장식 하나’라고 보고하면서 여러 장식을 요구하면 불일치다. 장식 개수 자체는 공통 고정값이 아니다.
5. **화면 보존:** 내용·글자·디자인·레이아웃을 유지하되 사진의 원근/빛과 최종 픽셀 동일성을 혼동하지 않는다. 실사 생성에서 `pixel-for-pixel`을 합격 기준으로 요구하지 않는다. 읽을 수 없는 글자는 미확인, 실제 픽셀 검사를 하지 않았다면 미측정이다.
6. **컨셉 밀도:** 제한 문장이 의도한 취향을 일반적인 생활 사진으로 희석하지 않는지 확인한다. 컨셉 요소의 개수보다 주변 요소들이 함께 만드는 인상을 설명할 수 있어야 한다.
7. **자율 추가 여지:** 상황에 자연스러운 세부 요소를 모델이 해석할 여지를 남긴다. 동시에 읽히는 임의 문구·브랜드와 화면을 가리는 요소는 허용 대상으로 미리 승인하지 않는다.

별도 검수자를 사용할 수 있으면 최종 문안과 같은 기준으로 독립 검수한다. 그렇지 않으면 작성과 검수를 별도 단계로 기록한다. 별도 검수자 또는 현재 대화의 총괄이 있어야만 이해할 수 있는 숨은 규칙을 두지 않는다. 검수자의 수정 제안도 최종 문서/문안에 남겨 다음 실행자가 재사용할 수 있게 한다.

취향 레퍼런스는 분석용과 생성 참조용을 구분한다. 이번 촬영 검증의 생성 참조는 컨셉당 동일 완성 화면만 사용한다. 생성 파일은 각 호출이 반환한 정확한 원본 경로로 저장하고 대조한다. 공유 폴더의 최신 파일을 추정해 복사하지 않는다.

## 6. 다른 컨셉에 적용

새 컨셉에도 같은 기록 구조를 적용한다. 귀여움의 니트·파스텔·캐릭터를 기본값으로 상속하지 않는다. 미니멀을 무조건 흰색, 풍경을 무조건 녹색으로 고정하지 않는다. 시각적 제안은 가설로 만들 수 있지만 앱 기능·템플릿 지원·실측 성과는 지어내지 않는다.

문서 적용 예시는 [컨셉별 설계 점검](../concept-direction-review.md)에 있다. 새 컨셉의 시각적 해석 가능성과 기존 실행 도구가 그 컨셉을 지원하는지는 별도로 확인한다.

배포 환경 검증 절차는 [main 환경 검증 계획](../concept-main-validation.md)을 따른다. 이 절차를 작성한 것과 실제로 통과한 것은 구분한다.
