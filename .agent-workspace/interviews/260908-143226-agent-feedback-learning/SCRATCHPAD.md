# 인터뷰 메모 — 에이전트 피드백 학습

## 맥락
- 사용자 요청: “나랑 같이 대화하며 구현 계획 구체화하자”
- 기존 계획: .omo/plans/marketing-knowledge-context.md (Revision 6, Draft).
- 새 논의 초안: .omo/drafts/agent-feedback-learning.md.
- Hermes 참고 커밋: 3a7bf7455f7da9ac2858475f9571652df642bc11.

## 주요 주제
- 기존 MarketingAgentService에 메모리·스킬·회고를 연결하는 사용자 경험.
- 저장했다는 사실과 실제 품질 개선을 구분.

## 결정사항
- 한 번에 질문 하나로 함께 구체화한다.
- 제품 코드는 수정하지 않는다. 앞선 assistant 제안은 사용자 확정 결정이 아니다.
- 기존 문서·코드의 다른 작업을 보존한다.

## 제약과 경계
- 현재 에이전트에 초점을 맞추며 hosted 피드백을 현재 기능으로 설명하지 않는다.
- private 대화의 shared workspace context는 read-only.
- 기존 팀 지식 계획과 중복되는 저장·권한·검색 소유권을 확인한다.

## 더 탐색할 영역
- [ ] 대표적인 반복 실수와 기대 동작
- [ ] 메모리·스킬·검증의 적용 범위
- [ ] 자동 학습 신호, 수정 권한, 충돌·복구
- [ ] 회고 시점·비용·우선순위
- [ ] 기존 지식 계획과 통합 경계 및 검증 기준

## 핵심 인용
- “에이전트 말하는 거야”
- “설명좀 깔끔하고 보기쉽게 해줘”

## 미해결 질문
- 명확한 사용자 수정은 다음 작업에 반영하도록 즉시 처리하고, 그 외 작업 경험은 일정량 모아 백그라운드에서 학습할 것인가?

## 인터뷰 교환 1
- 사용자: “아직 에이전트를 slack에 안 올려봐서 모르겠어”
- 확인: 사용자는 Slack 실사용 전이므로 반복 실수 사례를 제시할 수 없다. 실사용 실패를 추정하지 않는다.
- 진행: 실제 사례 요구를 중단하고, 원하는 동작을 가상 시나리오로 확인한다.
- 다음 질문: 답변 전 결과 검증까지 이번 계획에 포함할지 확인한다. 메모리·스킬 회고와 검증은 별도 기능이며 포함 여부는 아직 미합의다.

## 인터뷰 교환 2
- 사용자: “학습만”
- 확정: 이번 구현 계획은 학습 기능만 다룬다. 답변 전 결과 검증 기능 추가는 제외한다.
- 학습 기능 자체의 동작 검증(저장·재사용·권한·복구)은 구현 QA에 포함하며 제품의 결과 검증 기능과 구분한다.
- 다음 질문: 사용자 지적뿐 아니라 에이전트가 스스로 발견한 유용한 작업 방법도 학습 대상으로 삼을지 확인한다.

## 설명 교환 — 검증의 의미와 트레이드오프
- 사용자: “검증은 뭐야?” → 검증은 이번 결과를 출처·실행·산출물 등으로 확인하고, 학습은 다음 작업의 기억·절차를 갱신하는 기능으로 설명.
- 사용자: “검증까지 진행하면 트레이프 오프는?”
- 현재 확정 범위는 여전히 “학습만”. 질문을 검증 추가 승인으로 해석하지 않는다.
- 검토할 선택: 객관적으로 확인 가능한 작업에만 검증 적용 vs 모든 결과에 적용.
- 설명 기준: 오류 발견 기회와 학습 근거의 질 / 지연·비용·추가 실행 / 객관적 확인과 모델 자기평가의 차이 / 재시도 종료 조건. 숫자 추정은 측정 없이 제시하지 않는다.

## 설명 교환 — 검증 빈도와 Hermes 범위
- 사용자: “검증은 에이전트가 대답할때마다 하는 거야?” → 제안은 매 답변이 아니라 확인할 작업 결과가 생겼을 때의 선택적 검증. 아직 범위에 추가하지 않음.
- 사용자: “hermes에도 이런 기능이 있어?”
- Hermes SHA 3a7bf745의 verification_stop.py를 직접 재확인: 코드 수정 후 fresh passing evidence가 없을 때 조건부 재검증을 요구하는 opt-in 기능. 기본 OFF, auto는 messaging에서 OFF. 일반 조사·카피 등 모든 작업을 동일하게 자동 검증한다는 근거로 확대하지 않음.
- 확정 범위는 학습만 유지.

## 인터뷰 교환 3 — 확장 제외
- 사용자: “확장은 하지말자”
- 확정: 조사 출처·보고서 등 범용 결과 검증 확장을 추가하지 않는다. 이전 “학습만” 범위를 유지한다. Hermes의 코딩 검증 기능을 도입한다는 뜻도 아니다.
- 기존 에이전트 실행 검증과 개발 QA는 그대로이며 새로운 제품 검증 기능은 계획하지 않는다.
- 다음 질문: Hermes의 학습 신호 중 사용자 지적 외에 실제 해결한 작업 방법도 자동 학습할지 확인한다.

## 인터뷰 교환 4 — 학습 신호
- 질문: “Hermes처럼 사용자 지적뿐 아니라, 작업 중 시행착오 끝에 알아낸 유용한 방법도 스스로 저장하도록 할까요?”
- 사용자: “응”
- 확정: 사용자 지적과 실제 해결한 작업 경험 모두 자동 학습 대상. 해결되지 않은 시도를 검증된 방법으로 저장하지 않는다. 새로운 결과 검증기를 추가하는 의미는 아님.
- 다음 소유자 결정: 공용 메모리·스킬을 바꿀 수 있는 팀원 범위. Private DM에서 shared context는 read-only라는 기존 불변식은 유지.

## 인터뷰 교환 5 — 공용 학습 권한
- 질문: “팀 공유 대화에서는 팀원 누구의 피드백으로든 공용 메모리·스킬을 자동 갱신할 수 있게 할까요?”
- 사용자: “응”
- 확정: 기존 인증·채널 admission을 통과한 모든 팀원의 공유 대화 피드백이 공용 학습 근거가 될 수 있다. 관리자만 수정 근거를 제공하는 별도 제한은 두지 않는다.
- 유지: 개인 DM으로 공용 메모리·스킬을 변경하지 않는다. 발언 모두를 무조건 규칙으로 저장한다는 뜻은 아니며, 학습 여부·적용 범위는 회고가 판단한다.
- 다음 질문: 같은 적용 대상에 대한 상충 피드백 처리. 범위·맥락으로 해소되지 않는 충돌에서 확인할지 결정한다.

## 범위 확인 — 단일 Slack 워크스페이스의 공용 에이전트
- 사용자: “이건 slack 워크스페이스에 팀원들이 1개의 에이전트를 쓸떄는 가정한 거지?”
- 설명: 지금까지 논의한 기본 단위는 Slack 워크스페이스 하나에서 여러 팀원이 하나의 공용 에이전트를 사용하는 경우다. 연결·허용된 공유 대화의 공용 메모리·스킬을 공유하며 스레드별 대화/작업은 구분한다. 개인 DM은 공용 기억 수정 대상이 아니다.
- 이 메시지는 범위 확인 질문이며, 직전 피드백 충돌 처리 질문의 답변이 아니다. 충돌 처리 결정은 대기한다.

## 인터뷰 교환 6 — 충돌 확인
- 사용자: “응 확인하도록 해줘”
- 확정: 같은 적용 범위에 대한 피드백이 충돌하고 대화 맥락으로 해소되지 않으면 해당 학습 변경을 보류하고 팀에 확인한다. 단순히 최신 발언으로 덮어쓰지 않는다.
- 원래 대화/스레드에서 확인하는 방식을 제안 기본값으로 둔다. 전 채널 broadcast나 새로운 외부 메시지 전송을 지금 실행하는 승인은 아니다.
- 다음 질문: 학습 변경의 사용자 알림 여부. 실제 반영과 보류/실패를 구분해 알린다.

## 인터뷰 교환 7 — 조용한 학습
- 사용자: “아니 안 알려줘도 돼”
- 확정: 메모리·스킬의 정상적인 학습 반영 알림은 Slack에 보내지 않는다.
- 유지: 같은 범위의 피드백 충돌을 해소할 수 없으면 팀에 확인한다. 무알림은 충돌 질문을 없애는 결정이 아니다.
- 내부 변경 이력과 반영/보류/실패 상태는 유지해 정확한 조회·복구가 가능하게 한다.
- 다음 질문: 즉시 반영해야 할 사용자 수정과 묶어서 처리할 작업 경험의 학습 시점.
