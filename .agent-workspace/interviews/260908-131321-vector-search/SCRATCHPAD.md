# 인터뷰 메모 — 벡터 검색 연결

## 맥락
- 기준: feature/marketing-knowledge-context 작업 브랜치.
- 목적: 구현 전에 벡터 검색의 요구사항과 구성을 대화로 결정한다.
- 프로젝트 interview 설정에 따라 이 인터뷰를 저장한다.

## 주요 주제
- 기존 키워드 검색에 의미 기반 검색을 연결하는 방법.

## 핵심 인사이트
- 현재 서비스는 KnowledgeRetriever(repository)를 생성하며 벡터 제공자를 연결하지 않는다.
- 기존 검색의 권한 검사와 출처·수정·삭제 반영을 함께 고려해야 한다.

## 제약사항 및 경계
- main이나 이전 설치 버전이 아닌 작업 브랜치를 기준으로 논의한다.
- 실행 직렬화 개선은 이번 인터뷰 범위에 포함하지 않는다.
- 구현 착수 요청은 아직 없다.

## 결정사항
- interview 방식으로 한 번에 질문 하나씩 진행한다.

## 긴장관계 및 트레이드오프
- 아직 미정.

## 더 탐색할 영역
- 원하는 검색 결과와 대표 사례.
- 검색 대상과 언어.
- 외부 임베딩 API와 로컬 처리의 경계.
- 규모, 갱신 시점, 운영 비용.
- 검색 결과 결합과 성공 판단 기준.

## 핵심 인용
- “일단 벡터 검색 연결하려면 어떻게 구성해야할까? $interview”

## 미해결 질문
- 키워드가 달라도 찾아주길 원하는 실제 질문과 자료의 예시는 무엇인가?

## 추가 대화 — 검색 시나리오와 대상
- 사용자 요청 예시: “귀여운 스레드 마케팅 게시물 만들고 싶어”
- 우선 검색 대상: “반응이 좋았던 게시물 + 레퍼런스”
- 브랜드·제품 정보를 제외한다고 결정한 것은 아니다. 이번 답변은 먼저 찾을 자료의 우선순위다.
- 구분할 요구: 귀여운 분위기·말투·이미지의 유사성과 게시물 성과의 근거.
- 다음 질문: 좋은 반응을 조회수·참여 반응·전환 중 어떤 기준으로 판단할지, 또는 사람의 평가를 사용할지.

## 추가 대화 — 성과 기준
- 사용자 답변: “조회수, 좋아요·댓글·공유, 클릭·가입 같은 전환,”
- 조회, 참여, 전환 지표를 모두 고려한다. 단일 지표 우선순위나 가중치는 아직 정하지 않았다.
- 구성 후보: 의미 검색으로 관련 후보를 찾고 별도 성과 데이터로 비교한다. 사용자 확정 사항은 아니다.
- 다음 탐색: 검색 대상 게시물·레퍼런스·성과 데이터의 현재 저장 위치와 접근 가능성.

## 추가 대화 — 기존 지식과 지정 문서 활용
- 사용자: “그건 에이전트 안의 메모리,wiki 같은 거나 에이전트한테 여기에 문서 있다고 해서 읽을 수 있지 않아?”
- 요구: 기존 메모리·Wiki와 사용자가 위치를 알려준 접근 가능한 문서를 활용한다. 사용자가 별도 저장소를 사전에 정하도록 요구하지 않는다.
- 구분: 문서를 읽는 경로와 읽은 내용을 검색 색인에 반영하는 경로를 연결해야 한다. 문서 위치를 알려줬다는 사실만으로 접근 권한이나 파싱 성공을 가정하지 않는다.
- 구성 후보: 기존 수집/추출 → 기존 검색 청크 임베딩 → 키워드+벡터 후보 결합 → 기존 권한·버전 검사. 성과 수치는 근거가 있는 경우만 비교하고 없으면 미확인으로 둔다.
- 다음 질문: 귀여움의 유사도를 글뿐 아니라 이미지까지 판단할 필요가 있는지.

## 추가 대화 — 범용 검색과 SQLite 벡터 방향
- 사용자 교정: “근데 왜 귀여운 에 집착하는 거야? 이거로 하드코딩할건 아니잖아?”
- 확정: 예시 문구나 마케팅 지표를 검색 규칙으로 하드코딩하지 않는다. 임의의 요청에 기존 지식을 검색하는 범용 기능이다.
- 사용자: “openclaw 방식대로 하려고 하는데 sqlite vector에”
- 방향: OpenClaw의 SQLite 벡터 검색 방식을 따른다. 공식 문서에서 sqlite-vec 기반 저장·검색과 임베딩 제공자 분리를 확인했다.
- 아직 미정: 임베딩 생성은 로컬 모델인지 외부 API인지. SQLite에 저장하는 선택만으로 생성 위치는 결정되지 않는다.
- 질문을 사례 세부 취향으로 확장하지 않고 실제 구성 선택에 집중한다.

## 추가 대화 — 선택 기능과 구현 여부 구분
- 사용자: “아 그럼 무조건 필요한 기능이 아니야?” → 벡터 검색은 선택 기능이며, 선택할 경우 임베딩 모델이 필요하다고 설명했다. 외부 API는 필수가 아니다.
- 사용자: “openclaw에서도 확장 가능으로 남겨놓은 거야?”
- 확인: OpenClaw는 임베딩 제공자와 벡터·하이브리드 검색 경로가 구현되어 있으며, 제공자 미설정 시 키워드만 사용한다. sqlite-vec 가속은 선택이며 미사용 시 프로세스 내 코사인 비교로 대체한다.
- Trace는 현재 작업 브랜치에서 VectorSearchPort 인터페이스는 있으나 실제 제공자를 연결하지 않은 상태이므로 OpenClaw의 선택 가능한 완성 기능과 구분한다.
- 아직 벡터 검색 도입이나 임베딩 제공자를 최종 결정하지 않았다.

## grep.app 실제 소스 확인
- 사용자: “openclaw에서는 어떻게 구현해놨어? grep_app으로 확인”
- grep.app searchGitHub에서 openclaw/openclaw 저장소로 범위를 제한하여 확인했다. 검색 인덱스의 main 소스이며 특정 배포 버전 실행 검증은 아니다.
- embeddings.ts / manager-provider-lifecycle.ts: 임베딩 제공자 생성과 provider none의 FTS-only 경로.
- manager-embedding-ops.ts: 문서 embedBatch 호출. manager-embedding-cache.ts: provider/model/provider_key/hash별 임베딩 캐시.
- manager-sync-base.ts: vec0 가상 테이블 생성, id TEXT PRIMARY KEY와 embedding FLOAT[dimensions].
- manager-search.ts: vec0 KNN 후보 조회와 코사인 점수. 코드 주석의 시간복잡도 주장은 검증하지 않았으므로 반복하지 않는다.
- hybrid.ts 및 src/agents/memory-search.ts: 벡터/키워드 결과 결합. 확인된 기본 가중치 0.7/0.3, MMR 활성화.
- 명시된 제공자의 장애는 무조건 키워드 검색으로 조용히 대체하는 정책이 아니며, 설정과 실패 종류에 따라 오류를 보고한다.

## 추가 대화 — 임베딩 사용의 설정 부담
- 사용자: “임베딩 모델을 직접 연결을 해야지만 사용이 가능한거야?”
- 구분: 벡터 검색에는 임베딩 모델이 필요하지만 사용자가 코드를 직접 작성할 필요는 없다. OpenClaw는 제공자 연동이 구현되어 있어 지원되는 API 키/모델 설정 또는 로컬 모델 설정으로 사용할 수 있다.
- 앞서 확인한 공식 문서상 기본 OpenAI 키가 이미 설정되어 있으면 별도 memory 설정 없이 활성화 가능. 로컬은 해당 제공자·모델 준비가 필요하다.
- Trace 작업 브랜치는 제공자 연동과 벡터 색인 구현이 아직 필요하며, 구현 후 설정만으로 쓰는 형태를 목표로 할 수 있다. 구현이나 제공자 선택을 최종 승인한 것은 아니다.

## 추가 대화 — 로컬 임베딩 구성
- 사용자: “로컬 모델 써도 돼? 그럼 어떻게 해야 할까?”
- 로컬 임베딩 사용을 검토 중. 모델·실행기 최종 선택이나 구현 착수는 아직 확정하지 않았다.
- 가능한 구성: 에이전트 서버의 로컬 임베딩 실행기(Ollama 또는 llama.cpp) → SQLite sqlite-vec 저장 → 기존 FTS와 결합.
- 로컬 모델 역할은 검색용 임베딩이며 기존 대화·판단 모델과 구분한다.
- 필요한 구현: 임베딩 제공자, 기존 인덱싱 작업에 벡터 생성/갱신/삭제 연결, VectorSearchPort 구현·주입, 모델 식별/캐시/재색인 관리.
- Ollama 공식 문서에서 /api/embed의 배치 입력과 저장/질의 동일 모델 사용을 확인. OpenClaw 공식 문서에서 local llama.cpp 제공자를 확인.
- 다음 질문: 실제 에이전트 운영 머신과 RAM/GPU 사양. 개발자 Mac을 실제 배포 머신으로 가정하지 않는다.

## 보류 및 작업 전환
- 사용자: “일단 이건 나중에 해야겠다. 일단 지금 에이전트의 부족한점을 찝어줘 저장소 쪽은 지금 어느정도 MVP 수준까진 된 것 같으니”
- 벡터 검색 인터뷰와 도입 검토는 보류한다. 임베딩 모델·하드웨어·실행기는 결정하지 않았다.
- 새 요청: 현재 작업 브랜치 기준으로 저장소 이외 에이전트 기능의 부족한 점을 읽기 전용으로 평가한다. 저장소의 MVP 완성 여부를 별도로 인증한 것은 아니다.
